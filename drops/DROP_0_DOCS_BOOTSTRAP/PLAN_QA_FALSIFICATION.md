## Blocking Findings

1. fail — C8 BOM pre-strip sed is a silent no-op on macOS BSD sed. U0.4 criterion 2 claims the pattern sed 1s with the hex escape \xef\xbb\xbf strips UTF-8 BOMs before the head and equality check, so a BOM-prefixed file does not silently break the match. This is FALSE on macOS. BSD sed does not interpret \xNN hex escapes in regex — that is a GNU sed extension. In single-quoted shell, the 12-char literal backslash-x-e-f-backslash-x-b-b-backslash-x-b-f is passed to sed; BSD sed compiles \x as just the letter x, so the overall pattern matches the literal 9-char string x-e-f-b-b-b-f at start of line, not the three BOM bytes 0xEF 0xBB 0xBF. The ci.yml primary test job runs on macos-latest, and the local dev QA gate is Darwin per the env preamble. A BOM-prefixed line-1 therefore passes straight through sed unchanged, head pipes the BOM bytes, and the equality vs hash-space-WIKI fails. The criterion still catches BOMs via outright failure, but the graceful tolerance it claims does not exist.

Mitigation: (a) use bash dollar-quoting so sed receives the real three bytes; or (b) drop the sed and rely on the builder-facing BOM-free directive alone, accepting the original P4 strictness which is what actually happens today; or (c) use perl -pe with BEGIN binmode STDIN then s/^\x{FEFF}// or awk NR==1 with sub on the three literal bytes — these are portable across BSD and GNU. Option (b) is simplest and most honest.

2. fail — U0.2 criterion 1 exactly 1 H1 match is a builder footgun. The criterion requires grep -c returns exactly 1 for pattern caret-hash-space-Valv-em-dash-Project-space-CLAUDE.md. But the grep is code-block-unaware: any fenced code block or prose example that displays the title literal at column 0 counts as an additional match. A rewrite that includes a Title conventions section demonstrating the H1, or any markdown example block with a sample file header, will produce count = 2 and fail the criterion. Construction: if the rewrite has the real H1 on line 1 plus any example line at column 0 matching the same title literal inside a code fence or blockquote, count = 2 and criterion fails.

Mitigation: change returns exactly 1 to returns at least 1 — the spirit is Valv-branded H1 present, not no literal self-reference anywhere. If the intent is specifically to catch duplicate H1s (as F2-R2 rationale suggests), the tighter check is head -1 FILE piped to grep -cE pattern returns exactly 1, which pins the H1 to line 1 without policing the rest of the file.

3. fail — U0.5 criterion 3 describes column shape that contradicts criteria 2, 6, and 7. Criterion 3 says each row has columns for at minimum: drop number, name, state, blocked_by, one-line scope, drop-dir link. Plain English implies drop-number and name are SEPARATE columns. But every other criterion assumes they are COMBINED into one leftmost cell:

   - Criterion 2 regex caret-pipe-spaces-DROP_ digits requires the first data cell to start with DROP_ followed by digits.
   - Criterion 6 per-edge greps caret-pipe dot-star DROP_N_SUFFIX dot-star pipe dot-star blocked_by require the compound name DROP_N_SUFFIX to appear before the blocked_by cell.
   - Criterion 7 awk -F with field separator class underscore-or-pipe assumes field 3 after split is the drop number, which only holds when the row format is pipe-space DROP_N_SUFFIX space-pipe — drop number and name combined in cell 1.

   A literal reading of criterion 3 leads a builder to render pipe-space-0-space-pipe-space-DOCS_BOOTSTRAP-space-pipe-space-building-space-pipe-space-em-dash-space-pipe-... which makes ALL OTHER criteria fail: crit 2 returns 0 (no line starts with pipe-DROP_), crit 6 per-edge greps return 0, crit 7 awk emits no rows so END condition exits 1. The builder is forced to rebuild against the regex rather than the English, but the English misleads them into failure first.

Mitigation: rewrite criterion 3 to match the required shape — the leftmost data cell is the full compound drop ID DROP_N_SUFFIX (drop number and name combined); subsequent cells hold state, blocked_by, one-line scope, drop-dir link. Or state the column order explicitly: columns, in order, are drop-id, state, blocked_by, scope, dir-link. The implicit column-order pin is load-bearing for criteria 6 and 7 — make it explicit.

## Concerns (non-blocking polish)

1. F3-R2 polarity check is direction-asymmetric. The pipeline grep -A 5 -E arrow_regex FILE piped into grep -cE no-cycles-or-strictly-layered includes the match line plus 5 lines AFTER. A builder who writes the polarity phrase BEFORE the arrow chain on two separate lines will fail the subcheck because the polarity phrase is above the match, not captured in -A 5 context. The criterion English within 5 lines of the DAG is ambiguous about direction; the grep is one-sided. Switching to grep -B 2 -A 5 would accept both orderings. Not blocking because a same-line rewrite (the natural form) captures both together.

2. F5-R2 awk silently fails on a markdown table header row labeled pipe-space-DROP_ID. A reasonable builder might include a header row like pipe-space-DROP_ID-space-pipe-space-STATE-space-pipe... followed by a markdown separator row then data rows. The regex caret-pipe-spaces-DROP_ matches the header (DROP_ID starts with DROP_). After gsub removes non-digits, field 3 on "ID " becomes empty string; the second awk compares empty-string to prev+1 under numeric coercion. The empty string coerces to 0 initially so the first row does not fail, but after prev is set to empty string, the next row (field=0 numeric) vs prev+1 (empty+1=1) fails the equality check. The awk exits 1 even though the table is well-formed by normal markdown conventions. A defensive tweak: restrict the first-awk match regex to require digits immediately, e.g. caret-pipe-spaces-DROP_-digit. Minor robustness concern — standard markdown tables usually use prose headers like Drop or Name not DROP_ID.

3. U0.6 criterion 5 English contradicts ls semantics. The text says ls .worklog piped into wc -l returns greater-than 1 because at least the pre-existing md and log files plus the new .FROZEN marker are present. But ls without -a does NOT list dotfiles — .FROZEN starts with a dot, so ls hides it. The criterion still passes (there are many non-dot pre-existing files) but the stated rationale is wrong: .FROZEN presence is verified by crit 1 explicit ls, not by crit 5. Rewrite the rationale to at least the pre-existing non-dotfile md and log files survive, and drop the .FROZEN reference from this criterion.

4. U0.2 criterion 13 is subsumed by criterion 10. Crit 10 zero-reject regex already contains mage install. Crit 13 regex alternation NEVER-run-mage-install or mage install also zero-rejects mage install via the second branch. Two criteria enforce the same rule. Keep crit 13 for the distinct prohibition rationale, but note the redundancy.

5. F4-R2 polarity subcheck is phrase-fragile. grep -A 10 heading-regex FILE piped into grep -cE authoritative-or-defers-to-or-source-of-truth passes if ANY of those three bare words or phrases appears within the 10-line context. If a builder writes a heading like Legacy AGENTS.md Historical Note with a body Previously authoritative, now deprecated, the word authoritative appears in the -A 10 window, subcheck passes, but semantic polarity is reversed. Risk is lower than F3-R2 because the domain is more specific but the subcheck is still polarity-fragile. Tighter phrasing would pin is-authoritative or AGENTS.md-is-the-source-of-truth as multi-word phrases rather than bare words.

6. U0.2 criterion 9 Charm-path floor-4 across 6 options is under-constrained. The regex lists six alternation branches: charm.land/fang/v2, charm.land/bubbletea/v2, charm.land/lipgloss/v2, modernc.org/sqlite, testcontainers, modelcontextprotocol/go-sdk — with a floor of 4. A builder could include all three charm.land branches plus modernc.org/sqlite and satisfy 4, skipping testcontainers (used by the integration tier) and modelcontextprotocol/go-sdk (a core adapter dep). Consider raising the floor to 5, or splitting into Charm floor-3 plus non-Charm floor-2 gates.
