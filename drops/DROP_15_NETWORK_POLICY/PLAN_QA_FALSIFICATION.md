# QA Falsification Review

## 1. Findings
- 1.1 FAIL — Unit 15.2.5 assumes `.valv/tools.toml` is project-scoped, but the committed overlay path still resolves it from the raw current working directory. `resolveProjectImage` passes `workingDir` directly to `tools.Resolve` ([internal/cli/operator_helpers.go](/Users/evanschultz/Documents/Code/hylla/valv/main/internal/cli/operator_helpers.go:440), [internal/cli/operator_helpers.go](/Users/evanschultz/Documents/Code/hylla/valv/main/internal/cli/operator_helpers.go:462)), and `tools.Resolve` just joins that directory with `.valv/tools.toml` ([internal/tools/resolve.go](/Users/evanschultz/Documents/Code/hylla/valv/main/internal/tools/resolve.go:27)). From `repo/subdir`, the manifest is missed, `len(manifest.Tools) == 0` short-circuits overlay selection, and any DROP_15 image-build allowlist policy is bypassed for the normal subdirectory-launch case. The plan does not add a unit to re-root manifest resolution to the detected project root.
- 1.2 FAIL — The Round 2 plan acknowledges that `host.docker.internal` over an internal Docker network is unproven for runtime ([drops/DROP_15_NETWORK_POLICY/PLAN.md](/Users/evanschultz/Documents/Code/hylla/valv/main/drops/DROP_15_NETWORK_POLICY/PLAN.md:200)), but Unit 15.2.5 uses the same topology for image builds without a corresponding gate: host-local proxy, proxy env, and `ImageBuildRequest.Network = <internal-network>` ([drops/DROP_15_NETWORK_POLICY/PLAN.md](/Users/evanschultz/Documents/Code/hylla/valv/main/drops/DROP_15_NETWORK_POLICY/PLAN.md:35), [drops/DROP_15_NETWORK_POLICY/PLAN.md](/Users/evanschultz/Documents/Code/hylla/valv/main/drops/DROP_15_NETWORK_POLICY/PLAN.md:36), [drops/DROP_15_NETWORK_POLICY/PLAN.md](/Users/evanschultz/Documents/Code/hylla/valv/main/drops/DROP_15_NETWORK_POLICY/PLAN.md:121)). The shared service return surface is only `proxy URLs`, `NO_PROXY`, `internal-network name`, and `cleanup handle` ([drops/DROP_15_NETWORK_POLICY/PLAN.md](/Users/evanschultz/Documents/Code/hylla/valv/main/drops/DROP_15_NETWORK_POLICY/PLAN.md:120)); it does not include an image-build-specific fallback if build steps cannot reach the host proxy on that internal network. `ImageBuildRequest` can carry build args and `--network` ([internal/adapters/docker/ops.go](/Users/evanschultz/Documents/Code/hylla/valv/main/internal/adapters/docker/ops.go:9), [internal/adapters/docker/ops.go](/Users/evanschultz/Documents/Code/hylla/valv/main/internal/adapters/docker/ops.go:70)), but nothing in the plan proves that is sufficient for buildx on the target platform.
- 1.3 FAIL — The required integration test for Unit 15.2.5 can go green without exercising the build path unless the plan explicitly forces a rebuild. `EnsureProjectImage` reuses an existing overlay image whenever the three freshness labels match and `NoCache` is false ([internal/services/images/service.go](/Users/evanschultz/Documents/Code/hylla/valv/main/internal/services/images/service.go:768), [internal/services/images/service.go](/Users/evanschultz/Documents/Code/hylla/valv/main/internal/services/images/service.go:776)). The plan requires a test proving that `go install` during image build is filtered by the proxy ([drops/DROP_15_NETWORK_POLICY/PLAN.md](/Users/evanschultz/Documents/Code/hylla/valv/main/drops/DROP_15_NETWORK_POLICY/PLAN.md:125)), but it does not require `NoCache`, a unique repository/tag, or other cache-busting. That leaves a concrete build/test-bypass path if a matching overlay image already exists locally.

## 2. Counterexamples
- 2.1 Subdirectory launch bypass. Reproduction: create `repo/.valv/tools.toml` with a tool entry and future `[allowlist]`; run `valv codex` or `valv claude` from `repo/subdir`; `resolveProjectImage` calls `tools.Resolve(subdir)` instead of resolving from the detected project root, so `.valv/tools.toml` is treated as absent and the overlay path is skipped. Result: the DROP_15 image-build allowlist contract is not applied for a normal subdirectory launch.
- 2.2 Image-build topology gap. Reproduction: implement Unit 15.2.5 exactly as planned with a host-local proxy, proxy build args, and `ImageBuildRequest.Network=<internal-network>`; run the integration build on a platform where buildx `RUN` steps on that internal network cannot reach `host.docker.internal`; the `go install` step cannot reach the proxy, and the plan offers no image-build-specific fallback analogous to Note A1. Result: Unit 15.2.5 can satisfy its code-shape acceptance and still fail its functional acceptance.
- 2.3 Cached overlay test bypass. Reproduction: build an overlay image once for a manifest/base pair so the three freshness labels match; run the planned Unit 15.2.5 integration test without `NoCache` and without a unique tag or repo; `EnsureProjectImage` returns `EnsureActionUpToDate` and never executes `docker buildx build`. Result: the test can pass without proving proxy-enforced build egress.

## 3. Summary
- 3.1 FAIL — Round 2 resolves the Docker proxy-arg question, and `go.dev/dl` is not required for `GOTOOLCHAIN=auto`, but the plan still has three unmitigated counterexamples: project-root drift for `.valv/tools.toml`, no image-build fallback for the unproven `host.docker.internal` over `--internal` topology, and an integration-test cache bypass. The plan needs another amendment before falsification can pass.

## TL;DR
- T1 Three confirmed plan gaps remain: subdirectory launches miss `.valv/tools.toml`, image-build proxy reachability on the internal network is still unproven with no fallback, and the required integration test can skip the build path through overlay cache hits.
- T2 Concrete reproductions exist for each gap, so this is a FAIL rather than an Unknowns-only review.
- T3 Docker’s predefined proxy args are validated, and `GOTOOLCHAIN=auto` uses module-proxy downloads rather than `go.dev/dl`, but those points are not enough to rescue the current plan.
